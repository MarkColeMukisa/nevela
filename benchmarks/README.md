# Nevela benchmark

How fast is an API that Nevela generates, next to the same API written by hand in Laravel?

Three apps, the same products API, the same database, the same load script. The results and how to read them are in the docs: [Benchmarks](https://nevela-docs.vercel.app/benchmarks/).

The design follows [Grit's benchmark harness](https://github.com/MUKE-coder/grit/tree/main/benchmarks) (MIT): the same scenarios, the same mix, the same production setup for Laravel, and the same rules for keeping it fair.

## The apps

| App | What it is |
|---|---|
| **Laravel** | Laravel 13 with a products controller written by hand: plain Eloquent, arrays, no API Resources, no policy. Nobody signs in. |
| **Laravel + Sanctum** | The same image, with the routes behind `auth:sanctum`. What signing in costs on its own. |
| **Nevela** | The Laravel app `create-nevela` makes (without the dashboard), with the products API generated by `nevela:resource` from one line of fields. Signed in as the administrator, as the dashboard is. Nothing in it is written by hand. |

All three answer the same requests with the same JSON: `page`, `perPage`, `sort` and `q` on the list, `{ data, meta }` back, and the same keys on a product. The Nevela app uses the package from this checkout (`packages/laravel`), so a run measures the code as it is now.

## Fair

- **Production shape.** nginx and PHP-FPM (8 workers per CPU), OPcache with its tracing JIT and `validate_timestamps=0`, `composer install --no-dev` with an authoritative classmap, `APP_DEBUG=false`, and `artisan optimize` at start. Persistent connections to Postgres, without TLS. Not `artisan serve`, and not Octane.
- **Same limits.** Every app gets the same CPUs and memory (`APP_CPUS`, default 1). One Postgres for all of them, with more CPUs (`PG_CPUS`, default 2) so the apps give out before it does, and with durability off so the disk isn't what's measured.
- **Same table.** Both migrations make the same `products` table. `run.sh` compares the two databases' tables before anything is measured, and stops if they differ.
- **Same rows.** 10,000 products, from a seeded generator (`seed/make.mjs`), so every machine gets the same ids, names and prices.
- **Reset every run.** The table goes back to the 10,000 rows before each run. The write scenario adds rows for good, and a table that grew makes the next run's count slower.
- **One app at a time.** The others are stopped, not idle.
- **Warm-up discarded.** OPcache, the JIT and the connections fill before the measured run.
- **Interleaved.** One run of each app in turn, then the next round, so a machine that slows down slows everyone down.
- **Median of three.** Never the best run.
- **k6 on the container network.** On Docker Desktop a published port goes through a proxy that gives out before the apps do.

## Scenarios

| Scenario | Request | What it exercises |
|---|---|---|
| `show` | `GET /api/products/{id}` | routing, signing in, one row by its key, JSON |
| `list` | `GET /api/products?page=N&perPage=20` | the same, plus 20 rows and a `count(*)` |
| `write` | `POST /api/products` | the request body, validation with a unique check, an insert |
| `mixed` | 85% list, 10% show, 5% write | closer to an API people read more than they write |

50 virtual users, 30 seconds a run.

## Running it

Needs Docker with Compose, Node, and about 4 GB of memory free.

```sh
cd benchmarks
./run.sh check        # every app answers every scenario; nothing kept
./run.sh              # 3 runs × 4 scenarios × 3 apps, about 35 minutes
node report.mjs       # the tables, from results/latest
```

Settings, as environment variables: `REPS` (3), `DURATION` (30s), `VUS` (50), `SCENARIOS`, `APPS`, `APP_CPUS` (1), `PG_CPUS` (2) and `FPM_WORKERS` (8). On a machine with more cores, Grit's limits are `APP_CPUS=4 PG_CPUS=8 FPM_WORKERS=32`.

It also runs on GitHub: the **Benchmark** workflow, by hand from the Actions tab, and on any pull request that changes this folder. The tables are in the run's summary and the raw results in its artifact.

## Reading the results

`report.mjs` gives each scenario's median requests a second and latencies, the CPU of the app and of Postgres in the middle of the run, and which of the two gave out first.

- **The app gave out:** the number is that app's ceiling on these CPUs.
- **The database gave out:** the number is where the database stopped. The app could go further, and the gap between two apps is wider than the row shows.
- Ratios are between apps measured in the same run, on the same machine. Where the runs of two apps overlap, the difference is called within the spread, not a win.

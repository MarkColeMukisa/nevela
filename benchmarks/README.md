# Nevela benchmark: the speed rally

How fast is an API that Nevela generates, next to the same API written by hand in Laravel, and next to Grit, Rust, Next.js and Bun?

Nine apps, the same products API, the same database server, the same load script. The results and how to read them are in the docs: [Benchmarks](https://nevela-docs.vercel.app/benchmarks/).

The design follows [Grit's benchmark harness](https://github.com/MUKE-coder/grit/tree/main/benchmarks) (MIT): the same scenarios, the same mix, the same production setup for Laravel, and the same rules for keeping it fair.

## The apps

| App | What it is |
|---|---|
| **Laravel** | Laravel 13 with a products controller written by hand: plain Eloquent, arrays, no API Resources, no policy. Nobody signs in. |
| **Laravel + Sanctum** | The same image, with the routes behind `auth:sanctum`. What signing in costs on its own. |
| **Nevela** | The Laravel app `create-nevela` makes (without the dashboard), with the products API generated by `nevela:resource` from one line of fields. Signed in as the administrator, as the dashboard is. Nothing in it is written by hand. |
| **Laravel + Sanctum, Octane** | Laravel + Sanctum on [Octane](https://laravel.com/docs/octane) with FrankenPHP (`Dockerfile.octane`), which keeps the app booted between requests. |
| **Nevela, Octane** | Nevela, the same way. |
| **Grit** | A plain `grit new --api` with `grit generate resource Product`, as [Grit's own harness](https://github.com/MUKE-coder/grit/tree/main/benchmarks) builds it (`apps/grit.sh`, Grit pinned to 3.581.0). Go, Gin and GORM. Its generated routes ask for staff, so it is signed in as its administrator with a JWT. Run as Grit's harness runs it: Sentinel, Pulse and Studio off, no Redis. |
| **Bun** | The Bun app from Grit's harness (`apps/bun`, MIT): `Bun.serve` and Drizzle, one process per CPU, on Grit's own table. Every products route checks a JWT, which reads no database: the lightest sign-in here, so it is a ceiling rather than like for like. |
| **Rust** | Axum, Tokio and sqlx (`apps/rust`), written for this rally to answer exactly as the Bun app does, with the same JWT check, on the same table. One release binary, one Tokio worker thread per CPU. sqlx is not an ORM: the queries are written out, as most Axum apps write them. |
| **Next.js** | The Next.js app from Grit's harness (`apps/nextjs`, MIT): App Router route handlers on Prisma, `next build` and the standalone server, one process per CPU, on Grit's table. The same JWT check as Bun added to every products route. |

Every app is signed in, as each framework generates its routes, apart from the plain Laravel baseline. Grit, Bun, Rust and Next.js name their routes Grit's way (`/api/v1/products?page_size=20`), and k6 is told so (`PREFIX`, `PAGE_PARAM`); the requests are otherwise the same.

**Limits off, nothing else.** k6 is one person at one address asking hundreds of times a second, which every app here would rightly refuse. Nevela's limits on the signed-in API are switched off through its settings (`NEVELA_API_PER_PERSON=0`, `NEVELA_API_PER_ADDRESS=0`); its other protections, the block list check, the scanner rules and the sealed activity log on every write, stay on as shipped. Grit's limits have no setting, so `apps/grit.sh` sets them to 0 in its own `internal/ratelimit/rules.go`, the table Grit says is where limits are changed. That is the only change made to Grit's generated code.

**Everything that grows is reset.** Before each run: the products, Nevela's activity log, its security log and the bell, and Grit's activity log.

The Laravel apps answer the same requests with the same JSON: `page`, `perPage`, `sort` and `q` on the list, `{ data, meta }` back, and the same keys on a product. The Nevela app uses the package from this checkout (`packages/laravel`), so a run measures the code as it is now.

## Fair

- **Production shape.** nginx and PHP-FPM (8 workers per CPU), OPcache with its tracing JIT and `validate_timestamps=0`, `composer install --no-dev` with an authoritative classmap, `APP_DEBUG=false`, and `artisan optimize` at start. Persistent connections to Postgres, without TLS. Not `artisan serve`. The Octane apps are the same, served by Octane on FrankenPHP with the same number of workers, each replaced after 500 requests (Octane's default).
- **Same limits.** Every app gets the same CPUs and memory (`APP_CPUS`, default 1). One Postgres for all of them, with more CPUs (`PG_CPUS`, default 2) so the apps give out before it does, and with durability off so the disk isn't what's measured.
- **Same table.** Both migrations make the same `products` table. `run.sh` compares the two databases' tables before anything is measured, and stops if they differ.
- **Same rows.** 10,000 products, from a seeded generator (`seed/make.mjs`), so every machine gets the same ids, names and prices.
- **Reset every run.** The table goes back to the 10,000 rows before each run. The write scenario adds rows for good, and a table that grew makes the next run's count slower.
- **One app at a time.** The others are stopped, not idle.
- **Warm-up discarded.** OPcache, the JIT and the connections fill before the measured run.
- **Interleaved.** One run of each app in turn, then the next round, so a machine that slows down slows everyone down.
- **Median of three.** Never the best run.
- **k6 on the container network.** On Docker Desktop a published port goes through a proxy that gives out before the apps do.

## Scenarios

| Scenario | Request | What it exercises |
|---|---|---|
| `show` | `GET /api/products/{id}` | routing, signing in, one row by its key, JSON |
| `list` | `GET /api/products?page=N&perPage=20` | the same, plus 20 rows and a `count(*)` |
| `write` | `POST /api/products` | the request body, validation with a unique check, an insert |
| `mixed` | 85% list, 10% show, 5% write | closer to an API people read more than they write |

50 virtual users, 30 seconds a run.

## Running it

Needs Docker with Compose, Node, Go, the Grit CLI at the pinned version, and about 4 GB of memory free.

```sh
cd benchmarks
go install github.com/MUKE-coder/grit/v3/cmd/grit@v3.581.0
./apps/grit.sh        # Grit's side, from its CLI (run.sh does it too when it is missing)
./run.sh check        # every app answers every scenario; nothing kept
./run.sh              # 3 runs × 4 scenarios × 9 apps, about three hours
node report.mjs       # the tables, from results/latest
```

`APPS="nevela grit"` races just those.

Settings, as environment variables: `REPS` (3), `DURATION` (30s), `VUS` (50), `SCENARIOS`, `APPS`, `APP_CPUS` (1), `PG_CPUS` (2) and `FPM_WORKERS` (8). On a machine with more cores, Grit's limits are `APP_CPUS=4 PG_CPUS=8 FPM_WORKERS=32`.

It also runs on GitHub: the **Benchmark** workflow, by hand from the Actions tab, and on any pull request that changes this folder. The tables are in the run's summary and the raw results in its artifact.

## Reading the results

`report.mjs` gives each scenario's median requests a second and latencies, the CPU of the app and of Postgres in the middle of the run, and which of the two gave out first.

- **The app gave out:** the number is that app's ceiling on these CPUs.
- **The database gave out:** the number is where the database stopped. The app could go further, and the gap between two apps is wider than the row shows.
- Ratios are between apps measured in the same run, on the same machine. Where the runs of two apps overlap, the difference is called within the spread, not a win.

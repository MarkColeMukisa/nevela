## The speed rally: who won

Nevela against Grit, Rust, Next.js, Bun and Laravel, each answering the same products API, signed in, on one CPU each and one Postgres. A pair of bars a rival, in the order they finished, the fastest first, and a tab for each scenario. Hover or tab to a bar for its runs and what held it back.

<RallyCharts />

Nevela runs here as it does at its fastest, on [Octane](https://laravel.com/docs/octane). Laravel's side is the same API written by hand, behind Sanctum, also on Octane.

**Nevela finished last.** Every rival served more requests a second than Nevela did. That was expected of the compiled ones and of Bun. It is less comfortable against Laravel itself, and the page says why [below](#where-nevela-loses-and-why).

## The contenders

Nine apps answer the same products API, one at a time, against one Postgres:

| App | What it is |
|---|---|
| **Rust** | Axum, Tokio and sqlx, written for this rally to answer as the Bun app does, with the same sign-in check, on the same table. One release binary, one Tokio worker thread per CPU. sqlx is not an ORM: the queries are written out, as most Axum apps write them. |
| **Bun** | The Bun app from [Grit's harness](https://github.com/MUKE-coder/grit/tree/main/benchmarks) (MIT): `Bun.serve` and Drizzle, one process per CPU. Every products route checks a signed token (a JWT). |
| **Grit** | A plain `grit new --api` with `grit generate resource Product`, as Grit's own harness builds it (Grit 3.581.0, Go, Gin and GORM). Its generated routes ask for staff, so it is signed in as its administrator. Sentinel, Pulse and Studio off, no Redis, as Grit's harness runs it. |
| **Next.js** | The Next.js app from Grit's harness (MIT): App Router route handlers on Prisma, `next build` and the standalone server, one process per CPU. The same JWT check as Bun added to every products route. |
| **Laravel** | Laravel 13, a products controller written by hand. Plain Eloquent and arrays, no API Resources, no policy. Nobody signs in. |
| **Laravel + Sanctum** | The same app with its routes behind `auth:sanctum`. What signing in costs on its own. |
| **Nevela** | The Laravel app `create-nevela` makes, with the products API generated by `nevela resource Product --fields="name:string, sku:string!, description:text?, price:money, stock:int, active:boolean"`. Signed in as the administrator, as the dashboard is. Not one line written by hand. |
| **Laravel + Sanctum, Octane** | Laravel + Sanctum, served by Octane on FrankenPHP instead of nginx and PHP-FPM. |
| **Nevela, Octane** | Nevela, the same way. |

PHP-FPM starts the app afresh for every request. Octane starts it once per worker and keeps it, so a request skips Laravel's startup.

Rust, Bun and Next.js check the token's signature and read nothing from the database to do it, the lightest sign-in here. Grit, Sanctum and Nevela look the user up on every request. So those three are a ceiling, not like for like: they show how fast the same answers can be, not what the same work costs.

## Results

Measured on 26 November 2026, [on a GitHub runner](https://github.com/MarkColeMukisa/nevela/actions/runs/45901640680), with Nevela as it is after 0.44.0:

```
machine: 4 CPUs (AMD EPYC 7763), 16 GB, Ubuntu 26.04
limits:  each app 1 CPU (8 workers for PHP-FPM or Octane), Postgres 2 CPUs
load:    50 virtual users, 30 seconds a run, 3 runs of each, the median reported
php 8.5.13, Laravel 13.44.1, Grit 3.581.0 on Go 1.26.11, Bun 1.3.5,
Rust 1.91 with Axum 0.8.9, Next.js 15.5.29 with Prisma 6.19.3
```

Requests a second (more is better), in the order the apps finished:

| App | `show` | `list` | `write` | `mixed` |
|---|--:|--:|--:|--:|
| Rust | 6,525 | 795 | 6,517 | 807 |
| Bun | 2,926 | 794 | 2,830 | 809 |
| Grit | 2,075 | 1,192 | 1,802 | 869 |
| Next.js | 362 | 204 | 420 | 198 |
| Laravel + Sanctum, Octane | 284 | 147 | 217 | 149 |
| Laravel | 198 | 132 | 168 | 126 |
| Nevela, Octane | 203 | 116 | 103 | 116 |
| Laravel + Sanctum | 149 | 105 | 131 | 102 |
| Nevela | 114 | 82 | 73 | 81 |

The scenarios: `show` is one product by its id, `list` a page of 20 and the total, `write` validates and inserts one, and `mixed` is 85% list, 10% show and 5% write. No app failed a single request.

What held each one back matters as much as the number:

- **The PHP apps and Next.js ran out of CPU everywhere, and so did Grit on `show`, `list` and `write`.** Their one CPU was at 100% while Postgres had room, so those numbers are each app's ceiling on one CPU.
- **Bun and Rust on `list` and `mixed`, and Grit on `mixed`, ran out of database.** Postgres was at 200%, both its CPUs, while the app had room. Counting 10,000 rows for every page is most of the work there, and about 800 a second is what this Postgres managed. Grit's `list` went past that with Postgres at half the load, so Grit asks it for less.
- **Rust on `show` and `write` didn't run out of either.** Its CPU was at 82 to 90%. The fifty users wait for each answer before asking again, and they couldn't ask any faster, so Rust's number there is a floor.

The three runs of each app were close. The charts show the slowest and fastest of them, and none of the rankings above falls within that spread, except Bun against Rust on `list` and `mixed`, where both hit the same database ceiling.

## What the numbers say

The matchups, in the order the rivals finished, each against Nevela on Octane.

**Rust, 7 to 63 times as fast.** The gap is widest where the database does least: one product or one insert, 32 and 63 times. Where both wait on Postgres it narrows to 7. A compiled binary with written-out queries and a sign-in that reads nothing is close to the most one CPU can do.

**Bun, 7 to 27 times.** A JavaScript runtime, and it served about half of what Rust did on single reads and writes, then tied it where the database was the limit.

**Grit, 7 to 18 times.** Grit is the fairest rival: a generated API, like Nevela's, that looks its user up on every request. Go and Gin do that work many times faster than PHP does.

**Next.js, 1.7 to 4 times.** The closest rival, and the only one that is, like Laravel, a full framework in an interpreted language. It still serves 1.7 times as many reads, and 4 times as many writes.

**Laravel, 1.3 to 2.1 times.** The same API written by hand, behind Sanctum, on Octane. This is the matchup that measures what Nevela itself costs.

## Where Nevela loses, and why

Nevela is a Laravel package, so it can't be faster than Laravel. The question is what it costs: how many requests a second an API generated by Nevela gives up, next to the same API written by hand.

| Scenario | Nevela against Laravel + Sanctum, PHP-FPM | The same, on Octane | Nevela on Octane against Nevela on PHP-FPM |
|---|--:|--:|--:|
| `show` | 0.77× | 0.72× | 1.78× |
| `list` | 0.78× | 0.79× | 1.42× |
| `write` | 0.56× | 0.48× | 1.42× |
| `mixed` | 0.79× | 0.78× | 1.44× |

**Signing in costs 18 to 25% on its own.** Putting the hand-written routes behind Sanctum takes that off. Every request looks up its token and its user. An API people sign in to pays this whatever it is built with.

**Reads cost Nevela about a fifth more than the hand-written app.** For one product, Laravel with Sanctum asks Postgres three things: the token, the user, the product. Nevela asks four: the same three and **the user's roles**, for the permission check. The generated code also does more in PHP: an API Resource for each product, a policy check, and, since step 11, a look at the block list on every request (from the cache, not the database) and a check of the path against what scanners ask for.

**Writes cost Nevela about half.** This is where Nevela is furthest behind, and further than it was. A write does three things the hand-written one doesn't:

- **It writes to the activity log, and seals it.** Since step 11 every entry is chained to the one before by a keyed hash, so nobody can quietly change the log. Writing one takes a transaction and a lock on the head of the chain, so writes to the log happen one at a time.
- **It reads the new product back** after inserting it, so the answer has every column as the database stored it.
- **It validates through a form request,** with the unique check on `sku`.

In [October's run](https://github.com/MarkColeMukisa/nevela/actions/runs/39249357784), on the same CPU, Nevela's writes were 0.83× of Laravel with Sanctum on PHP-FPM, and its reads 0.86 to 0.88×. The sealed log is the biggest change to the write path since then, but how much of the drop each piece accounts for hasn't been measured separately yet. That is the next speed step: the write path first, then the sign-in lookup, then caching.

**Octane makes Nevela 1.4 to 1.8 times as fast.** It gains most where a request does least, a single product, because there Laravel's startup was most of the work. Where speed matters, run Nevela on Octane: there it serves about as many single reads as hand-written Laravel with no sign-in does on PHP-FPM.

These are ceilings on one CPU. On that one CPU, a Nevela app still answers more than a hundred signed-in requests a second, every one checked against its roles and every change logged and sealed.

## Fair to all of them

The harness follows [Grit's](https://github.com/MUKE-coder/grit/tree/main/benchmarks), whose page this one is modelled on, and keeps its rules:

- **Production setup for every app.** For PHP: OPcache with its tracing JIT, a production Composer autoloader, `APP_DEBUG=false` and `artisan optimize`, behind nginx and PHP-FPM or on Octane with FrankenPHP, never `artisan serve`. Rust is a release build with link-time optimisation. Grit, Bun and Next.js are built as Grit's own harness builds them.
- **The same everything else.** The same CPU and memory for each app, the same Postgres, the same table for each family of apps (checked before anything is measured), the same 10,000 rows from a seeded generator, put back before every run.
- **One app at a time,** with the others stopped. A warm-up before each run, not counted. The apps take turns, so a runner that slows down slows them all.
- **The median of three runs,** never the best one.
- **The same question for each app.** The Laravel apps take the same `page`, `perPage`, `sort` and `q` as Nevela's and return the same `{ data, meta }`. Grit, Bun, Rust and Next.js answer Grit's API on Grit's table, with the same page size, and the Rust app returns the same shape of JSON as the Bun app.
- **Octane as it ships.** Each worker is replaced after 500 requests, Octane's default.

A shared GitHub runner is not a quiet machine, which is why the apps are compared within one run and not across runs. On another machine the numbers will differ, and the ratios between the apps should hold.

## Run it yourself

The harness is in the repository, under [`benchmarks/`](https://github.com/MarkColeMukisa/nevela/tree/main/benchmarks). It needs Docker with Compose, Node, and about 4 GB of free memory:

```sh
git clone https://github.com/MarkColeMukisa/nevela.git
cd nevela/benchmarks
./run.sh check     # every app answers every scenario; nothing kept
./run.sh           # about three hours, for all nine
node report.mjs    # the tables, from results/latest
```

It builds the Nevela app from the package in your checkout, so it measures the code as it is now. `APPS="nevela-octane rust"` measures fewer apps. On a machine with more cores, give the apps what Grit's harness does: `APP_CPUS=4 PG_CPUS=8 FPM_WORKERS=32 ./run.sh`.

It also runs on GitHub as the **Benchmark** workflow, by hand from the Actions tab and on any pull request that changes `benchmarks/`. The tables are in the run's summary.
